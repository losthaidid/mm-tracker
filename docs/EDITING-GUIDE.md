# Make your own small changes

Welcome, Haidid. Start with one small visual or wording change, check it on the website, then move
to the next. [The file map](FILE-MAP.md) shows which feature owns each file.

## The three kinds of code

| Kind | Purpose | Example |
| --- | --- | --- |
| HTML | Initial page structure and labels. | `<h1>SAP MM WorkHub</h1>` |
| CSS | Appearance: colour, size, spacing and layout. | `font-size: 1.8rem;` |
| JavaScript | Behaviour: open a form, calculate a total, save records. | `openModal('Company recipients', body);` |

Most screens are generated by JavaScript after sign-in. Their wording lives in their feature `.js`
file, even though the browser eventually displays HTML. `index.html` supplies the initial shell.

## Edit through GitHub

1. Open [your repository](https://github.com/losthaidid/mm-tracker).
2. Use the branch selector to create a branch, for example `my-title-change`, from the current `main`.
3. Open the file and select the pencil/Edit control. Use the example/search term below to find the code.
4. Make one change and commit it to your branch with a clear message.
5. Open a pull request into `main` and review **Files changed**. Merge when ready to publish.
6. Open **Actions** and wait for the GitHub Pages deployment for that merge to finish successfully.
7. Reopen [your website](https://losthaidid.github.io/mm-tracker/) and check the affected screen on
   your laptop and phone. If an old asset is cached, reload or change its `?v=` value as described below.

A branch lets you review the difference before it reaches the live site. With the current Pages
setup, merging into `main` publishes the change. The branch itself does not automatically provide a
preview website. GitHub's **History** shows previous versions if you need to compare or restore code.

## First edit: make the title larger

Open [custom.css](../custom.css). The examples are initially comments, so they do nothing. Activate
the first one by removing the `/* Example 1...` comment line and the closing `*/`, leaving:

```css
body #hubHeader #hubSiteTitle {
  font-size: 1.8rem;
}
```

Change `1.8rem` to `2rem` for a larger title. A selector identifies the element to style. A property
such as `font-size` names what changes. The value and semicolon finish the instruction.

`custom.css` loads last. A more specific selector can still win over a broad rule, so start with the
selectors provided in the examples. Browser **Inspect → Styles** shows which rule currently wins.

## Second edit: soften ticket corners

Add this to `custom.css`:

```css
body .workspace-v10 .ticket-queue-card {
  border-radius: 22px;
}
```

`22px` is a corner size. Try `14px` or `28px`. This changes ticket-card appearance and does not edit
any saved ticket. Keep each rule's opening `{` and closing `}`.

## Third edit: change a Settings description

Open [settings-panel.js](../settings-panel.js) and search for `const ITEMS`. Find:

```js
recipientSettingsButton: [
  'work',
  'Company email lists, ready to copy.',
  'recipients email address contacts to cc bcc company',
],
```

Change the description to `'Copy email addresses for each company.'`. The three values mean:
category ID, description, and search words. Keep `recipientSettingsButton` and `'work'` as they are
when only changing wording: the first identifies the existing button; the second chooses its group.

In `GROUPS`, `name` controls the visible category label and `note` explains that category. Keep `id`
when renaming a category so the existing actions still point to it.

## Fourth edit: change a generated screen sentence

Open [app.js](../app.js), search for `A clearer view of your support queue`, and replace just that
sentence inside its HTML template. Preserve the surrounding markup and `${...}` expressions.

```js
const name = 'Haidid';
const greeting = `Hello ${name}`;
```

The backticks create a template string; `${name}` inserts the value of `name`. In the application,
values inserted into HTML should pass through `esc(value)`. For plain DOM text, use `textContent`.
These prevent record text such as `<img ...>` from becoming executable markup.

For example, a field definition such as `['description', 'Description', 'textarea', true]` means:
keep the value under `description`, show the label Description, use a multiline input, and require
a value. Changing the visible label is a simple wording edit; changing the saved property name
requires matching form/save/upgrade changes.

## Settings versus code defaults

Use the website's Settings for your header title, Momo name, appearance, maintained lists, mileage
rates and company recipients. Those changes save to your account and are usually easier than code.

`studio.js → DEFAULTS` supplies fallback values, not an override of saved preferences. Changing a
fallback does not replace a value already saved in your account. Similarly, `index.html → seedData`
is empty starter data/default lists; it is not where your current tickets are stored.

Dropdown options can already be maintained in Settings. Changing an old seed/default list does not
necessarily update an account that already has its own list.

## Follow one button from click to save

Here is a simplified example of the pattern used in the application:

```js
// 1. A stable data attribute identifies the action. Its caption can be changed.
const button = '<button type="button" data-example="rename">Rename</button>';

// 2. An event handler finds the button, then opens a form.
// 3. The form handler reads and validates its values.
// 4. The shared adapter changes a draft, not the live state directly.
a.mutate(draft => {
  const record = draft.tasks.find(task => task.id === taskId);
  if (!record) throw Error('Task no longer exists.');
  record.task = reviewedTitle;
});
```

This is an explanation, not a complete paste-in feature: `a`, `taskId` and `reviewedTitle` must come
from the feature's existing adapter/form. The real save flow is:

1. `mutate()` clones the current account document and applies the edit to the draft.
2. `save()` runs preparation hooks such as derived context/timeline updates.
3. `saveCloud()` validates the document and stores a local recovery/pending copy.
4. `flushCloud()` sends it to Supabase with the known revision and mutation ID.
5. Save status updates; conflicting edits are merged conservatively or shown for review.

Rendering and navigation refresh the screen; they should not create uploads. Momo movement, audio,
visitor positions and open panels usually stay local. Finished work records and maintained account
settings use the shared save flow. See each feature's header comment for the distinction.

## Understand common names

| Name/pattern | Meaning in this project |
| --- | --- |
| `const` / `let` | A binding that stays fixed / can be reassigned. Objects held by `const` can still have properties changed. |
| `array.map(...)` | Make an output item for each input, often to build card markup. |
| `array.filter(...)` | Keep matching items, for example visible tickets. |
| `array.find(...)` | Find one record, usually by its stable `id`. |
| `install(a)` | Receive shared application functions through an adapter named `a`. |
| `upgrade(document)` | Add missing fields for older saved formats while keeping existing information. |
| `validate(document)` | Reject invalid values before saving or accepting an import. |
| `prepare(next, previous)` | Derive related changes before validating/saving the next document. |
| `data-action`, `data-hub`, etc. | Action identifiers read by event handlers. Keep them when only changing button text. |
| `esc(value)` | Escape text before adding it to generated HTML. |
| `root` | The browser/global object passed into a module wrapper, usually `window`. |
| `?.` / `??` | Safely read a possibly missing value / use a fallback for `null` or `undefined`. |

## Refresh a changed asset

The file reference can include a cache version:

```html
<link rel="stylesheet" href="./custom.css?v=20261019-source-1">
```

After editing `custom.css`, change the matching version in `index.html`, for example to
`?v=haidid-style-2`. The filename stays `custom.css`; `?v=...` tells the browser to request a new URL.
Change the matching script version when editing a JavaScript file too. If you change a linked image
or asset whose address is cached, update its version/reference as appropriate.

Keep dependency order: engines before their interfaces, `studio.js` before `app.js`, and
`custom.css` after other style sheets. The grouped comments in `index.html` explain each block.

## Work locally when you are ready

With Node.js installed, from a local clone:

```sh
npm ci
npm test
npm run format:check
```

`npm test` runs the regression suite with fake accounts and an isolated database; it does not edit
your real account. `npm run format` formats the handwritten root JavaScript/CSS and `index.html`.
The formatter checks syntax/style; it cannot prove that a new business rule is correct.

For a local browser view, serve the directory over HTTP, for example `python -m http.server 8080`,
and open `http://localhost:8080`. Use your tracker login only if you intend to access its real cloud
records: a local copy still points at the configured Supabase project. Follow Supabase redirect
configuration if testing authentication redirects on localhost.

`supabase-client.js` is a generated dependency. After intentionally updating its source/library,
`npm run build:client` rebuilds it from `cloud-entry.js`. Ordinary text/CSS edits need no build.

## A practical boundary for your first changes

Start with captions, descriptions, colours, spacing, corners and existing dialogue. When changing
field keys, IDs, relationships, validation, money/time calculations, SQL policies or autosave logic,
follow the existing upgrade/save pattern and run the relevant tests. A field that looks unused may
still be required by an older backup or a linked record.

To undo a published code change, revert its pull request/commit and wait for Pages to deploy that
revert. Code rollback does not roll back account data; use the website's Backup before experimenting
with changes that intentionally modify records.
